Goal

Find out whether a stranger can run your project from your documentation alone, and do the same for another team. A team that cannot be onboarded from its README is not ready to ship.

This is a group assignment, graded individually. The team turns in one submission. [TEAM] rubric rows are shared and [INDIVIDUAL] rows are graded per student. Requirements are in the Cross-Team Check-ins and the Onboarding Test section of the Project 03 guide in cst438-docs.

Who visits whom

Each team visits one team and hosts one team. The Project 03 Groups, Repos, Etc. page lists the pairings and every team's repo. The same pairings are used again at check-in 2.

Split your team: some members visit while at least one member stays to host, then swap at the halfway call. Every member visits once and hosts once.

Before class (hosts)

  • Your repo is public and the default branch is the version you want tested.
  • The README and docs/runbook.md explain how to clone, configure, run docker compose up and run the tests. Anything a visitor needs (an .env.example, seed data, test-only credentials) is in the repo or the README says where to get it. Real secrets never go in the repo.
  • Create an onboarding label in your repo so visitors can use it.

In class

Visitors, on your own laptops, using only the host team's README and runbook:

  1. Clone the repo and follow the documented steps (for example git clone, then git switch to the branch the README names, if it names one).
  2. Reach a working local stack with docker compose up and open the app or the API.
  3. Run the test suite.
  4. Keep a log of every command you ran and what happened. The timebox is set in class.

Hosts may answer questions out loud but may not touch the visitors' keyboards. If an answer was needed, the README was missing it, and that is an issue.

Filing onboarding issues

Visitors file every blocker as a GitHub issue in the host repo, labeled onboarding. One issue per problem. Each issue includes:

  • The step in the README or runbook where it happened.
  • The exact command and the exact output or error (paste text, not only a screenshot).
  • What was expected instead.
  • The visitor's OS and Docker version.

If nothing blocked you, file one issue saying so, with the commands you ran. "It didn't work" is not an issue.

Hosts: before the end of class, acknowledge every onboarding issue filed against you (assign an owner or reply with a plan). Before the Final Submission, fix or answer every one of them; that part is graded on the Final Submission.

Turn in (one per team)

A PDF or a text entry containing:

  • Your team number, the team you visited and the team that visited you.
  • Which members visited and which hosted in each half.
  • Issues you filed on the host team: a link to each one and the name of the visitor who filed it.
  • Issues filed on you: a link to each one, its owner, and whether the visitors reached a running stack and a green test run.
  • The visitors' command log.
